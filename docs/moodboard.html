01

What we keep, what we drop

Minecraft's UI is two things fused together: a very good interaction and extension model, and a 2011 pixel-art skin the model happens to wear. Hytale is the existence proof that they separate. Mojang's own Ore UI is the second proof, and it has not reached the container screens yet.

Keep as DNA

  • The slot mental model. Carried stack, left/right/shift semantics, drag painting, number-key swaps, double-click collect. Seven click modes, implemented once.
  • Menu / Screen split. Server-side slot logic with client prediction and a state-id resync. Screens only draw and translate input.
  • Container slots first, then player slots. One index space, one routing table for quick-move.
  • Item stack = id + count + component patch. Mergeable iff same id and same patch; stack size is data.
  • Theming as data. The 9-slice-as-sidecar idea generalises to a token file: roles like panel, slot, slot-hover, tooltip-frame map to materials a pack can swap.
  • Resource packs and datapacks. Layered asset overrides, namespaced ids, JSON recipes and tags, composable patch lists from Bedrock's JSON-UI.
  • The modding surface. Screen injection, exclusion zones, tooltip components, HUD layers, custom widgets. Section 05.
  • The item browser lineage. R/U lookup, prefix search, bookmarks, transfer with dry-run, recipe categories. Section 08.

Drop as skin

  • The 320×240 virtual canvas and integer GUI scale. Keep a UI scale knob, but layout is flex and grid in real pixels, responsive to window height like AE2's tall terminal.
  • 18 px slot pitch, 176×166 panels. Slots become a token, 40 or 48 px, gap 4. Panels size to content.
  • Bevels. Depth comes from soft shadows at three elevation levels and a 1 px inner top highlight, not from two-tone borders.
  • Bitmap 8 px font. A grotesque for body and a condensed face for counts and headings, tabular numerals, variable weights.
  • 16 px sprites. 3D-rendered icons with a fixed rim-lit rig, baked once to an atlas. Diablo IV documented exactly this move for legibility.
  • Purple gradient tooltip box. A two-tier tooltip card: compact on hover, expanded on dwell or Shift, clamped to the viewport.
  • Fixed hardcoded slot coordinates. Slot positions come from layout, and both logic and rendering read the same slot definition.

Hytale, the proof

Early access since January 2026. Minecraft interaction model, modern skin, crafting folded into the inventory screen, cursor highlight that follows across every grid (Update 5), redesigned tooltip cards (Chapter 1 preview). Its GUI system is data-driven and skinnable, as the HyUI mod shows.

Ore UI, the gap

Bedrock's React-based UI defines Mojang's new language: rounded, flat, translucent dark panels, green hero buttons, controller hints. Menus and settings have migrated. Container and inventory screens have not. The Modern UI mod for Java, with 8.5M downloads, shows the audience wants blur, rounded tooltips and smooth fonts.

03

Vocabulary and motion

Glass over a world

Blur alone fails on a busy scene. Tint the panel 10–30%, keep one shared border token, keep slots opaque, and measure text contrast against the tinted panel, not the raw scene. Blur is a panel-level effect: render the scene, downsample to a quarter, run a dual Kawase pass, sample it in a UiMaterial. Never blur per node.

Rarity, twice

WoW, Diablo and Destiny converge on grey, white, green, blue, purple, gold. Colour alone fails colour-blind players, so encode rarity a second way: an inner ring plus a corner glyph, a stamp, or a bottom bar. Make the colours user-configurable.

Two-tier tooltips

Compact card at 120–150 ms hover: name, rarity, count, mod badge. Expanded on dwell or Shift: stats, tags, id, "used in". Alt-click opens the encyclopedia page. Clamp to the viewport, Stardew's known flaw.

Motion budget

200–280 ms · cubic-bezier(.2,0,0,1) stagger

Reduced motion: durations to 0–80 ms, no fly-to-slot.

Gamepad changes the slot

Snap-focus grids need a nav graph between panels and a focus ring drawn outside the slot so rarity borders stay visible. Slots need focused, focused-and-held for split, and selected-for-move states. Expose Sort, Quick Stack, Deposit and Loot as buttons with glyph hints. A Destiny-style magnetic cursor suits the browser better than the grid. Tap targets 40 px and up for Steam Deck touch.

Icons and type

3D-rendered icons with a fixed three-point rig and a cool rim from behind, baked once at 64–128 px to an atlas and cached to disk. Flat items become extruded quads for the same treatment. Body in a grotesque, counts and headers in a condensed face with tabular numerals. Keep a flat monochrome icon set for chrome.

05

Extension points the plugin set must expose

Screen injection is the single most important one. Mods add buttons, slots and overlays to screens they do not own. Everything else is a registry.

Screen lifecycle events

Fabric fires BEFORE_INIT and AFTER_INIT per screen instance and lets you subscribe to before and after render, tick, remove, mouse and keyboard with allow-cancel semantics; Screens.getButtons is a mutable widget list. Forge adds Init.Post with addListener and ContainerScreenEvent.Render with the panel origin.

Bevy: ScreenOpened<T>, ScreenLayout, ScreenClosed as entity events on the screen root, with named anchor children a mod can parent into.

Exclusion zones

Sophisticated Backpacks registers its tabs "as UI elements so recipe viewers can reposition their overlays". JEI draws a debug shadow over them. This is a first-class query, not a plugin courtesy.

Bevy: an ExclusionZone marker on any node; the browser and HUD union them per frame.

Custom widget trait

owo-ui's Component and LibGui's WWidget show the shape: measure, layout, draw, input, tooltip. owo-ui also has flow, grid and stack layouts with fixed, content, fill and expand sizing, insets, .animate() on any property, and XML models with hot reload.

Bevy: entities with Node already give layout for free. The trait is about behaviour and theming hooks, not drawing.

Tooltip components

ClientTooltipComponent lets a tooltip contain arbitrary drawn content: bundle grids, shulker previews, map previews, food icons, rarity frames. Tooltips can be multi-column and positioned away from the cursor.

Bevy: tooltip is a scene built from a list of components each with a builder; frame decorators wrap the result.

HUD layers

NeoForge's RegisterGuiLayersEvent names every vanilla layer and lets mods insert above, below or replace by id. Fabric's HudLayerRegistrationCallback does the same. Position editors (Jade, MiniHUD) write anchors to config.

Bevy: an ordered layer registry with built-in ids; each layer is a UI root with an anchor component.

Slot injection

Curios and Trinkets add slot groups to the player inventory menu and screen, and break when another mod replaces that screen. The menu extension and the screen anchor have to be one registration.

Bevy: a SlotGroupProvider registry consumed by both the menu builder and the screen template.

The interaction model, unchanged

Vanilla, valence and azalea implement the same seven-mode state machine over a slot list. This is the contract the model crate implements once, generically; individual menus only supply slot rules and a quick-move routing table.

Plus the chest toolbar

  • Sort must group by category then name; Enshrouded's gap-removing sort is the anti-pattern.
  • Quick stack moves stacks into containers that already hold that item, animated (Terraria).
  • Deposit all excludes hotbar, armour and offhand; Loot all is the inverse.
  • Favorite lock via Alt-click: skipped by sort, trash and quick stack.
  • Mouse Tweaks behaviours (drag-paint, wheel move) are expected, not optional.
  • Stack size, mergeability and result-slot rules are data on the item and slot, as in vanilla's component model and valence's validate_click_slot.
07

Architecture precedents

Menu vs Screen

Server-side menu owns slots, carried stack, click rules and quick-move. Client screen draws and translates input. Client predicts, sends ClickContainer { state_id, slot, button, mode, changed_slots, carried }, server diffs and resyncs on mismatch. Ghost items are what happens when this races with hopper ticks.

valence_inventory

Inventory { kind, slots: Box<[ItemStack]>,
            changed: u64 /* dirty bitmask */ }
OpenInventory { entity, client_changed }
ClickSlotEvent { slot_id, button,
  mode: ClickMode, slot_changes, carried }

Validation is a pure function per mode with a conservation-of-items check. Best Rust reference.

Bedrock JSON-UI bindings

Grids bind to engine collections (inventory_items, hotbar_items), controls inherit via child@namespace.parent, packs compose through modifications lists, inputs are abstract actions. The data-binding and patch ideas survive into a modern skin untouched.

Datapack shape

{ "id": "minecraft:diamond_sword",
  "components": {
    "minecraft:damage": 100,
    "minecraft:enchantments":
      { "minecraft:sharpness": 3 } } }

Recipes, tags and loot as JSON under namespaced paths. RON assets can mirror this one to one.

Factorio lifecycle

Data stage: all mods share one Lua state, run data.lua → updates → final-fixes in dependency order, then prototypes freeze. Control stage: per-mod VM, event bus, serialised storage. NeoForge does the same with registry events. Frozen registries are what make browser lookups pure and cacheable.

Pain to design out

  • Slot coordinates duplicated between menu and screen
  • Quick-move boilerplate per menu
  • Two constructors per menu
  • 16-bit container properties
  • Texture API churn breaking every GUI mod each release
08

The item browser

Fifteen years of convergent design from TooManyItems to EMI, plus Factorio's answer. The modern version is Factoriopedia-shaped: merged entries, deep links, history, "used in", rendered as cards with 3D icons rather than a wall of 16 px sprites.

What survived every generation

  • Side panel with paging and a search box; @mod, #tag, $tooltip prefixes, - negation, quotes, OR
  • R for recipes, U for uses, A to bookmark, Backspace to go back
  • Recipe categories with catalysts, ingredient cycling, focus highlight
  • Transfer button with dry-run, red highlights on missing slots
  • Ghost drag from the list into filter slots; cheat mode gated by server permission

Plugin API lessons

  • Ordered registration phases: subtypes → ingredient types → categories → recipes → transfer → screen handlers → runtime
  • The unit is an ingredient, a typed comparable key, not an item stack. Fluids, energy and info pages flow through the same index
  • Screen handlers per screen kind: bounds, exclusions, clickable areas, stack under cursor, ghost drop
  • A runtime object (filter text, visible entries, bookmarks, key mappings) so AE2-style terminals can sync

Scale and juice

  • Tens of thousands of entries once variants expand: per-prefix indexes, suffix tree or trigrams for names, bitsets for mod and tag, results cached until filter or visibility changes, built off-thread
  • Render only the visible page; icons from the baked atlas
  • EMI's recipe tree with base-ingredient totals, craftable-only mode, recipe favorites, quick-craft binds
  • Card hover pop, detail pane slide-in, staggered reveal on page change

What Bevy 0.19 gives us

Current release 0.19.1. The sibling crates here pin 0.17 and the jump is a real migration. The good news for a modern skin: the primitives are SDF and shader based, not texture based, so the look we want is cheaper here than a pixel-faithful one would be.

Rendering the look

  • BorderRadius and BoxShadow are SDF-based: rounded slots and three elevation levels with no atlases
  • BackgroundGradient, BorderGradient, per-side BorderColor: rarity rings and hero buttons
  • UiMaterial: one quad per slot with SDF border, glow falloff and an animated legendary shimmer; tanks and progress fills
  • Panel blur: scene → quarter-res dual Kawase → sampled in a UiMaterial
  • ViewportNode: live 3D preview for the hovered item, books and tool stations; bake the grid icons offline
  • Parley text with variable fonts, underline, FontSmoothing; TextShadow; pickable text sections
  • Known corner-bleed artifact with rounded children over differently coloured parents (#17561)

Interaction and structure

  • Pointer<Press/Click/Drag*/DragDrop> bubbling entity events; Hovered, Pressed, Checked, InteractionDisabled state components
  • Headless bevy_ui_widgets: button, slider, checkbox, scrollbar, list box, menu, popover; EditableText for search fields
  • TabGroup, TabIndex, AutoDirectionalNavigation: gamepad grid focus nearly free
  • ZIndex, GlobalZIndex, UiTargetCamera for layering; UI ignores RenderLayers
  • bsn! templates with patches and inline observers; no .bsn file loader yet
  • bevy_tweening 0.16 for lenses over Node, UiTransform, colours; core Val and Color interpolation
  • Unified 2D/3D UI is an open design issue (#22345); in-world UI today means render-to-texture on quads

Scripting shape

Four shapes exist in long-lived moddable games. Data plus named hooks fits an ECS best, with an imperative escape hatch for dynamic content. Screen injection from section 05 has to be reachable from scripts, or modders will lose the freedom the catalogue documents.

String DSL

Luanti formspec
list[current_player;
     main;0,4.85;8,1;]
listring[]

Easy to transmit, no retained state. Luanti is replacing it with a retained styled tree. listring is worth keeping.

Imperative tree

Factorio LuaGuiElement
gui.relative.add{
  type="frame",
  anchor={gui=defines
    .relative_gui_type
    .container_gui,
    position="right"},
  tags={id="sorter"}}

Relative GUIs anchored to vanilla screens are Factorio's screen injection. Copy tags and anchor.

Data + hooks

WoW · Starbound · Balatro
{ n = G.UIT.R,
  config = { align="cm" },
  nodes = { … } }

Layout as data with inherits, behaviour as named callbacks. WoW's taint model is a 20-year-old permission system for scripted UIs.

Data only

JSON-UI · datapacks · Patchouli

No sandbox concern, no language to learn, composable by patch lists. The floor of the pyramid: every data-only mod, including whole books and themes, should need no script.

Embedding

bevy_mod_scripting 0.20: reflection-driven bindings, scripts as hot-reloaded assets, callback labels, per-script contexts, dynamic components. Tracks Bevy 0.18, no wasm. bevy_scriptum 0.11 is the smaller model where exposed functions are Bevy systems.

Recommendation from the research: Luau behind a curated, versioned API namespace; data stage → freeze → control stage; scripts declare screens as data and answer events with commands, never direct mutation; a chained AssetReader for resource packs; Fluent for strings.

A modded screen as a Lua table, sketch

-- mods/sorter/data.lua  (data stage)
slotted.register_widget("sorter:button", {
  inherits = "slotted:icon_button",
  icon = "sorter:icons/sort.png",
  tooltip = { key = "sorter.tooltip" },
})
-- inject into every container screen we don't own
slotted.inject("slotted:container_screen", {
  anchor = "title_end",            -- named anchor
  children = {{ type = "sorter:button", tags = {act="sort"} }},
  exclusion = true,                -- publish our rect
})
-- mods/sorter/control.lua  (control stage)
slotted.on("widget_activate", function(ev)
  if ev.tags.act == "sort" then
    -- command, validated by the authority
    return slotted.cmd.sort(ev.screen.inventory("block"),
                         { by = {"category","name"} })
  end
end)

slotted.on("tooltip_build", function(ev)
  if ev.item.tags["c:foods"] then
    ev.add({ type="appleskin:food_row", item=ev.item })
  end
end)

Named anchors and exclusion come from section 05; inherits from WoW; tags from Factorio; the tooltip component hook from Fabric's TooltipComponentCallback. The same trees are expressible as RON for script-free mods.

A shape that is starting to show

Not a plan. The outline the research keeps pointing toward, revised for the modern direction.

model

Slots and stacks

UI-free, network-agnostic. Stack as id + count + patch, inventories as slot lists with a dirty bitmask, seven click modes plus sort, quick stack, deposit and loot, quick-move routing, slot behaviour enum (real, ghost, filter, output, locked), state-id resync.

ui

Widgets, theme, motion

On bevy_ui 0.19. Slot grid and virtual grid, item renderer with baked 3D icons, tank and bar materials, side tabs, tooltip composer, carried-stack layer, HUD layer stack, 3D viewport widget, pan-zoom canvas. A token-based theme (roles → materials) loaded from RON, with the three directions as shipped themes. One motion system with a reduced-motion switch.

browser

Factoriopedia layer

Depends only on the ui crate's screen handler API. Ingredient registry, recipe categories with layout builders, ordered phases, exclusion zones, dry-run transfer, prefix search over bitsets and a substring index off-thread, typed bookmarks, recipe tree.

script

Mods

Luau through a curated API. mod.toml, namespaced ids interned at freeze, data → freeze → control, screens and injections as data trees with named anchors, events out and commands in, tooltip and HUD hooks, chained asset reader for packs, Fluent.

Open questions

  • ?Which direction do we commit to first? Glass is the most expected; paper is the most distinctive; neon is the most fun. The theme system must make the other two cheap later.
  • ?Blur behind panels needs a scene-side pass. Is it a feature of the ui crate or an optional companion, since not every game wants to pay for it?
  • ?Where does the screen-injection API live: on the screen root entity as events plus anchors, or as a registry consulted at template spawn? Both, probably, but which is primary?
  • ?Do we bake 3D icons at startup, at asset-processing time, or ship a bake tool? Cache invalidation on model or texture change matters for modders.
  • ?bevy_flair CSS versus our own RON token theme. Flair gives selectors and transitions now; our own format gives control and BSN alignment later.
  • ?Is a pan-zoom canvas and a Markdown book engine in scope for v1, or are they the first "mod-like" crates built on the extension API to prove it?
  • ?In-world UI: wait for Bevy's unified UI, or ship render-to-texture-on-a-quad now for terminals and displays?

Where the six research passes agree. Keep the interaction model and the extension model, drop the skin. Slot layout lives in one place for logic and rendering. Theme is data with role tokens. The browser's unit is an ingredient. Registries freeze before play. Screens publish their rectangles and anchors so anything can be injected. Scripts declare and react, never mutate. Motion has a budget and an off switch.
