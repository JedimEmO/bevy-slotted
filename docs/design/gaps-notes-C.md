# Gap notes C: icons, fonts, advisories, wasm size

Package C of the gap-closing pass. What it covers: `IconDef::Model` and the
glTF bake, the two bakes' shared description, when the bake rig stops, the
shipped OFL fonts, the `ttf-parser` advisory, the playground's wasm size, and
a clean-clone CI run.

## 1. `IconDef::Model` loads a glTF

`Model` used to parse, warn and draw the missing glyph. It now takes a cell in
the atlas like any other icon, and with the `gltf` feature the GPU bake loads
the scene through the asset server and lights it under the same three-point
rig as the primitives.

The format gained a stand-in:

```ron
icon: Some((
    model: "models/pickaxe.gltf",
    shape: "rod", color: "#6b4c33", accent: "#d0d6dd",
    metallic: 0.6, roughness: 0.4,
))
```

`IconDef::Model` is now `Model { path, stand_in: Option<ShapeIcon> }`, and the
shape fields beside `model:` are read into that stand-in. It does three jobs at
once, which is why it is one field and not three:

- it is what the CPU bake draws, so a headless run, a snapshot test and a build
  without `bevy_gltf` all show a legible pickaxe rather than a hole;
- it is what the bake draws for the first frames, before the scene has loaded;
- its `shape` picks the view angle and the cell fill the *model* is rendered
  at, so the two pictures sit in the cell the same way.

A `Model` with no stand-in gets `shape::model_stand_in`: a box in a colour
hashed from the path. Bounding-box shaped on purpose. The real silhouette of a
glTF is not knowable without loading and projecting it, and the CPU bake has to
work with no renderer and no asset server at all.

**The model.** `assets/models/pickaxe.gltf`, five kilobytes, generated by
`tools/gen-demo-model.py` and committed. Three boxes and two materials,
flat shaded, one buffer embedded as a `data:` URI so the asset is a single
file. Written here rather than sourced, so the repository ships no third-party
3D asset and there is nothing to attribute. `minecraft:iron_pickaxe` in the
demo data is the item that uses it.

**Fitting.** A glTF is whatever size its author made it, so a model cell is two
entities: the outer one holds the cell position, the view rotation and a scale,
the inner one holds the scene (`WorldAssetRoot`, which is what Bevy 0.19 calls
what used to be `SceneRoot`) and an offset that centres the model on its own
bounds. Once the scene has spawned meshes, `fit_bake_models` measures it
from the mesh assets and the local transform chain — not from
`GlobalTransform`, so the answer does not depend on whether propagation has run
since the scene spawner did its work — and writes the offset and the scale. The
model is normalised to a unit cube first, which is what makes `cell_fill` mean
the same thing for a glTF as for a primitive.

**A path nobody shipped.** The fit pass also watches each scene's load state.
A failed load warns once, naming the item's model, and stops being waited on
immediately rather than holding the rig open for the full timeout; the cell
already holds the stand-in the CPU bake drew, so the atlas is right either way.

**Render layers.** Bevy does not propagate `RenderLayers` to children, so the
same pass puts the bake layer on every entity the scene spawner created.
Without it a model's meshes sit on layer 0 and draw into the game's own camera,
which is a bug that only shows up as a pickaxe floating in the world.

**Feature.** `slotted-icons/gltf` (facade: `slotted/gltf-icons`), off by
default. `bevy_gltf` — and `bevy_world_serialization`, which it pulls in — is
module size a game with no item models should not pay, and the playground in
particular drops it on purpose. Without the feature a `Model` warns once and
draws its stand-in.

## 2. One description, both bakes

`BakedAtlas.shapes: Vec<ShapeIcon>` became `BakedAtlas.cells: Vec<CellDraw>`,
where `CellDraw` is either a shape or a model-with-stand-in. Both bakes read
that one list, and the view angle (`shape::view_rotation`) and the cell fill
(`shape::cell_fill`) moved out of the GPU module into `shape.rs` beside the
polygons that are authored to match them. Colour, orientation and size are now
decided once.

What is still authored twice is the geometry: the CPU bake's flat polygons
against the GPU bake's `Mesh` primitives. They are drawn from the same
viewpoint at the same scale and are indistinguishable at 64 px, but a seventh
`ShapeKind` still has to be added to both. Generating the silhouette by
projecting the mesh would remove that, and it is a bigger change than this
package: it would move `Mesh` construction into the no-renderer path and it
would rewrite every accepted atlas snapshot. Left open, and narrowed: the
follow-up now names the geometry rather than the whole drawing.

## 3. The rig stops when it has drawn, not after 240 frames

The old rig rendered for a fixed `WARMUP_FRAMES = 240` and then switched its
camera off. The number was a guess with a wide margin around an unobservable
event: a mesh pipeline is specialised and compiled asynchronously, so the first
frames after the rig appears draw nothing, and switching off too early leaves a
blank atlas forever.

There is an observable signal, and it is now used. `report_bake_progress` runs
in the **render world**, in `RenderSystems::Cleanup` — after the render node has
drawn, so a frame it reports is a frame that was submitted. It finds the bake
camera's own `BinnedRenderPhase` for `Opaque3d` and `AlphaMask3d`, walks their
batch-set keys, and asks `PipelineCache` how many of those keys have a pipeline
in `CachedPipelineState::Ok`. The counts go back to the main world through an
`Arc<AtomicU32>` pair rather than an extraction, because it is two counters and
an entity id.

### The warm-up camera

Knowing when the rig has drawn is only half of it. The other half is a bug the
240-frame version had all along, found by re-running the chest capture twenty
times: about one shot in ten came out with every icon missing.

**A camera clears its target on the first frame it renders.** The rig's target
*is* the atlas, and it is handed to the renderer holding the CPU bake so a
screen opened during the bake still shows flat icons. But the moment the
camera renders, that picture is gone — replaced by nothing at all until the
pipelines finish compiling. The comment claiming the CPU bake was a safety net
was simply wrong; the camera was destroying it.

So the rig now has **two** cameras, identical in every way that a render
pipeline is keyed on — same scene, same materials, same projection, same
target format — differing only in order, target and whether they start active:

- the **warm-up camera** draws into a one-cell scratch image nobody looks at,
  and runs from the first frame. A pipeline key does not depend on the
  target's size, and the orthographic projection is fixed, so every mesh is in
  its frustum however small the image is.
- the **atlas camera** is off until the warm-up camera reports that every
  pipeline is compiled. Then it clears the atlas and refills it in the same
  frame.

The stages, in order:

1. wait for every glTF to load and be fitted;
2. wait for the warm-up camera to report a non-empty phase with every
   batch-set key in `CachedPipelineState::Ok`, twice running;
3. hand over: warm-up off, atlas camera on;
4. wait for the atlas camera to report the same, twice running, then switch it
   off.

Stage 1 matters because a scene that has not loaded contributes no batch set,
so an atlas of one model would otherwise "finish" on frame one with an empty
phase. The doubled frames in stages 2 and 4 are cheap insurance on a backend
that binds a newly compiled pipeline a frame late.

`BAKE_TIMEOUT_FRAMES` (600, ten seconds at 60 Hz) is a backstop, not the
mechanism. On timeout the rig warns with the pipeline counts, whether the
atlas camera ever ran, and the paths of any model still loading. If the
hand-over never happened it leaves the atlas camera off on purpose: keeping
the CPU bake beats clearing it to draw a partial picture.

In practice the rig finishes in a handful of frames instead of four seconds.
Twenty consecutive chest captures came out identical to within 0.1% of file
size, against one blank in ten before.

### What made it intermittent, and how the fix was checked

The integration review reached the same cause independently and pinned down
what decided whether a given run failed: **the shader cache**. The window
between the atlas camera's first clear and its first successful draw is exactly
as long as pipeline compilation takes, and that is seconds on a cold cache and
milliseconds on a warm one. The chest example captures at a fixed
`SHOT_AT = 2.0` seconds, so a warm machine almost always beat the deadline and
a cold one almost never did. Five captures with a fresh driver cache gave a
blank first shot and four good ones; five more on the warm cache gave five good
ones. That is why the bug looked like one in ten rather than like a plain
ordering mistake, and it is why a re-run always "fixed" it.

The evidence for the two-camera fix is `tools/check-shot.py`, which does not
compare file sizes: it counts the pixels inside nine known-filled slot rects
that differ from that rect's own median colour, with the stack count
deliberately outside the box so a slot printing "64" over a hole still fails.
A good capture scores 41 to 163 per slot; a wiped atlas scores zero on all
nine, so the two are an order of magnitude apart rather than a percentage. It
runs as `just shot-check`, and `just shot-chest` runs it after every recapture.

Five rounds of `just shot-chest`, each with `__GL_SHADER_DISK_CACHE_PATH`
pointed at an empty directory so every round compiled its pipelines from
scratch, produced 25 captures with icons in all of them.

The headless half of the same question is
`crates/slotted-icons/tests/review_gaps.rs`: every baked cell has ink in it,
and the rig's target starts as the CPU bake pixel for pixel rather than as an
image of the right size full of zeroes. Those two are what a future change to
the rig would trip over without needing a GPU.

## 4. Fonts

The three themes named type families and shipped no files, so every theme
rendered in Bevy's built-in face and the direction was invisible. Five OFL
families now ship under `assets/fonts/<family>/`, each with the `OFL.txt` it
was published with, and the themes' `fonts` blocks point at them:

| Theme | `body` | second token |
| --- | --- | --- |
| glass | Manrope | `display`: Barlow Condensed SemiBold |
| paper | IBM Plex Sans | `mono`: IBM Plex Mono Regular |
| neon | Manrope | `display`: Rajdhani SemiBold |

`glass` had no `fonts` block and no `font:` on any text role, so both were
added; the display face carries counts, badges, status and hints, which is
where a condensed numeral face earns its place.

All six files come from `google/fonts` `ofl/`. The two variable files were
renamed from their upstream `Family[axes].ttf` form so no asset path contains
brackets.

**Where they ship: in the repository, not in a crate.** No `slotted-*` crate
has an `include` for assets — `assets/themes/*.theme.ron` is not published
either — and a game copies the directory it wants. So published crate sizes are
unchanged, and a consumer pays for the fonts only when it asks for them.
`cargo deny check licenses` reads crate manifests and never sees these files;
the OFL obligation is met by the `OFL.txt` beside each family and by
`assets/fonts/README.md`. A theme that would rather ask the OS can drop `path:`
and set `system: true`, which needs Bevy's `system_font_discovery`.

## 5. `ttf-parser` (RUSTSEC-2026-0192)

The advisory was left unignored on the grounds that an `ignore` entry would
hide the next advisory on the same crate. It does not: a `cargo deny` ignore is
keyed by advisory id, so `RUSTSEC-2026-0192` mutes exactly that one and a
second advisory on `ttf-parser` still fails the check. That was the whole
objection, and it was wrong.

The other thing worth recording is where the crate comes from.
`cargo tree -i ttf-parser` reads:

```
ttf-parser <- owned_ttf_parser <- ab_glyph <- sctk-adwaita <- winit <- bevy_winit
```

It is winit's Wayland client-side window decorations, arriving through winit's
default features. It is not Bevy's text stack, nothing in this workspace can
reach it, and no `cargo update` moves off it because 0.25.1 is the last release
there will be. The exit is upstream: winit dropping `sctk-adwaita`, or Bevy
pinning winit without default features.

So: a dated, single-id ignore with the reasoning in the file, review
**2027-03-06**, and `cargo deny check` is now part of `just ci` (a new `just
deny` recipe) so the next advisory shows up on the branch that introduced it
rather than months later.

## 6. Wasm size

The playground's Bevy feature list was shared between the wasm build and
`cargo run -p web-playground`, so a wasm module compiled winit's x11 path and a
native run compiled WebGL2. They are now split into
`[target.'cfg(not(target_arch = "wasm32"))'.dependencies]` and
`[target.'cfg(target_arch = "wasm32")'.dependencies]`, which is the one Bevy
feature that genuinely differs between the two.

**It saves nothing.** Both sides were built from the same tree, on the same
day, so the comparison is real:

| Stage | `x11` on wasm too | split (`x11` native only) |
| --- | --- | --- |
| `cargo build --profile wasm-release` | 62.25 MiB | 62.24 MiB |
| after `wasm-bindgen` | 54.40 MiB | 54.39 MiB |
| after `wasm-opt -Oz` | 26.58 MiB | 26.57 MiB |

About ten kilobytes, which is noise. winit picks its backend by `cfg`, so the
x11 path was never in a wasm32 module in the first place and the feature only
ever selected code the target could not compile. The split is still worth
keeping — it is one fewer thing to build and it stops the manifest from
claiming something untrue — but it is a hygiene change, not a size one, and
the follow-up that asked for it should be closed as measured rather than as
fixed.

Everything else the profile can do it already does: `opt-level = "z"`, fat LTO,
one codegen unit, `panic = "abort"`, debuginfo stripped, and `wasm-opt -Oz
--enable-bulk-memory --enable-nontrapping-float-to-int` in `xtask`.

`strip = "symbols"` was considered and not tried. wasm-bindgen reads the
module's symbol names to find its exports, so stripping before it runs is the
one place stripping actually breaks something; and `wasm-opt -Oz` already drops
the name section afterwards, so there is no byte left for it to win. The 26.57
MiB module is a whole Bevy renderer, and the next real cut is Bevy's feature
surface, not the profile.

### Precompiling the mods' Luau bytecode

Investigated and **not** attempted; here is the design and why it stops.

The idea: compile each bundled mod's chunk to Luau bytecode at build time, ship
a VM without `luaur-compiler`, and save the 3.4 MiB the compiler costs.

It does not work as stated, for two independent reasons.

1. **`luaur-rt` cannot load bytecode and cannot drop the compiler.**
   `Chunk::into_function` always calls `luaur_compiler::compile` first;
   `ChunkMode::Binary` exists only for signature parity with mlua and is
   documented as unsupported. The `luau_load` FFI entry point that takes
   bytecode is reachable but private, and `luaur-compiler` is a
   non-optional dependency of `luaur-rt` with no feature gating it out. Both
   halves are upstream changes: a public bytecode loader, and a `compiler`
   feature.

2. **The playground needs the compiler at runtime anyway.** Its whole point is
   editing a mod's Lua beside the canvas and reloading it. That path compiles
   text in the browser. Shipping a compiler-less VM would remove the feature
   the page exists to show.

So the trade is only available to a *game* that ships fixed mods and no
in-game editor, and only after upstream exposes the two APIs. If both landed,
the shape would be: an `xtask precompile-mods` step writing `<mod>/<entry>.luac`
beside each script, `ModWatch` preferring the `.luac` when it is newer than the
source, and a `slotted-script-luaur/compiler` feature (default on) that a
release build turns off. That is worth writing down and not worth building
against an API that does not exist.

## 7. Clean-clone CI

`git clone` into a temp directory, then copy over every path a commit would
carry — modified, added, and untracked-but-not-ignored — so the checkout is
"the tree as it would be after committing", not the last commit. Then run the
gates there.

`just deny`, `just gen-docs-check` and `just wasm-check` all pass from cold;
`just wasm-check` includes `slotted-icons --all-features`, so `bevy_gltf` on
wasm32 is covered. `just fmt-check` and `just lint` fail, both inside
`slotted-ui`/`slotted-browser` work that was in flight from another package at
the time, and neither in a file this one touches.

Nothing failed for want of a file. The `examples/chest/assets` symlink is a
tracked symlink and clones as one; `assets/fonts/`, `assets/models/` and the
generated Lua reference are all present; `dist/` is not needed by any gate.
`cargo deny check` and `gen-docs-check` both pass from cold.

`just ci` now runs `cargo deny check` as a `just deny` recipe, and the CI
workflow gained the same step through `EmbarkStudios/cargo-deny-action`.

## Left open

- The two bakes' **geometry** is still authored twice (section 2). The shared
  description is done; projecting the meshes for the CPU silhouette is not.
- A model's stand-in cannot be derived from the glTF. It is declared or it is a
  box. Deriving it would mean a build-time step that loads the model and writes
  a silhouette into the data file.
- The `ttf-parser` ignore has a review date, not a fix.
