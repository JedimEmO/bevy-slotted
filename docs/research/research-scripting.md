# Research report: scripting and modding architecture for moddable Minecraft-style Bevy UI/inventory plugins

Date: 2026-09-05

## 1. Scripting in Bevy today

### bevy_mod_scripting (BMS) — the de-facto standard
- Repo: https://github.com/makspll/bevy_mod_scripting · Book: https://makspll.github.io/bevy_mod_scripting/ · docs.rs: https://docs.rs/crate/bevy_mod_scripting/latest
- Latest release 0.20.0 (2026-06-24). Compatibility table in README: BMS 0.19+ → Bevy 0.18; 0.18 → Bevy 0.17; 0.14 → Bevy 0.16; 0.11.1 → Bevy 0.15.3. BMS pins the Bevy patch version because bindings are code-generated per Bevy release. (Bevy 0.19 is current per bevy_fluent/wasvy dependency versions; a BMS release for 0.19 was not confirmed at time of research.)
- Languages via features: `lua51/52/53/54`, `luajit`, `luajit52`, `luau`, `rhai`. Rune is "temporarily on hold" after the 0.9 rewrite. All Lua flavours come through mlua.
- Platforms: Windows/Linux/macOS. WASM: explicitly unsupported (issue #166).
- Binding model: everything is driven by `bevy_reflect`. Scripts hold `ReflectReference`s (pointers to Components, Resources, Assets or owned values). Functions are registered into a dynamic function registry with `NamespaceBuilder::<T>::new(&mut world).register("name", |args| ...)` or `NamespaceBuilder::<GlobalNamespace>::new_unregistered(...)`; the `#[script_bindings]` macro cuts boilerplate and harvests doc comments. Argument types: primitives, `R<T>`/`M<T>`/`V<T>` (ref/mut/owned reflect), `ScriptValue`, and optional `FunctionCallContext` (gives world access). Reserved metamethod-style names: get/set/add/sub/mul/div/rem/neg/pow/eq/lt/iter/display/debug. `bevy_<crate>_bindings` features (ecs, transform, pbr, …) are generated by `bevy_api_gen` from Bevy's reflected type registry.
- Script lifecycle: `asset_server.load::<ScriptAsset>("x.lua")` (bytes only, no eval). Evaluation happens on attachment: `ScriptComponent` on an entity (EntityScript) or `AttachScript`/`DetachScript` commands (StaticScript). Attach/detach emit `ScriptAttachedEvent`/`ScriptDetachedEvent`; a `ScriptLoadingPipeline` handles init/reload/cleanup; contexts are per-script or shared, and removed when the last script leaves. Hot reload rides on Bevy's asset `file_watcher` feature — edit the .lua and it reloads.
- Callbacks: define with `callback_labels!(OnEvent => "on_event")`, fire with `ScriptCallbackEvent::new(OnEvent, args)`, run `event_handler::<OnEvent, LuaScriptingPlugin>` in a schedule. Order producers before the handler or events spill to the next frame. Built-ins: `on_script_loaded`, `on_script_unloaded`, `on_script_reloaded`. Responses come back via `ScriptCallbackResponseEvent` (includes entity). Globals in scripts: `world`, `entity`, `script_id`.
- ECS access from Lua: `world.query():component(A):component(B):with(C):without(D)` (ScriptQueryBuilder), `world.get_component`, `spawn`, `insert_component`, `get_resource`, `get_type_by_name`, etc. Access is guarded by `WorldCallbackAccess` with runtime access tracking (aliasing checks, so a script cannot hold two mutable refs).
- Dynamic systems (experimental): `system_builder("name", script_id):query(...):resource(...):exclusive():after(x)` then `world.add_system(schedule, sys)`; scripts can also register new components (`register_new_component`). Non-exclusive script systems only see the declared params; you cannot mutate the schedule you are currently running in.
- Performance: continuous benchmarks on bencher.dev (assets/benchmarks). The cost model is reflection + dynamic dispatch per field access, so per-frame per-entity scripting is expensive; event/callback-driven use is the sweet spot. No published absolute numbers in README.
- Code quality: clippy-enforced no unwrap/expect/panic/todo. ~650 GitHub stars, active.

### bevy_scriptum
- https://github.com/jarkonik/bevy_scriptum · https://jarkonik.github.io/bevy_scriptum/ · 0.11.0 (2026-03-07), Bevy 0.18.
- Runtimes: LuaJIT (mlua), Rhai, Ruby via magnus (Linux/macOS only). `app.add_scripting::<LuaRuntime>(|r| r.add_function("name", |In((a,)): In<(f32,)>, query: Query<...>| ...))` — exposed functions ARE Bevy systems, so they take normal Query/Res params. Promise-based returns (`:and_then(...)`), `entity` global, hot reload. Much smaller API surface than BMS; no reflection-driven binding of arbitrary components (you expose explicit functions). Good "small surface, curated API" model for modding.

### Others
- bevy_mod_js_scripting (deno_core, by Fishfolk/jumpy): dead. Fishfolk's punchy used deno_core V8 with only ECS access exposed — a precedent for untrusted-mod JS. https://github.com/fishfolk/punchy/wiki/Scripting
- wasvy (https://github.com/wasvy-org/wasvy): WASI/Component-Model modding for Bevy, "just hatched", mods compiled to `wasm32-wasip2`, interfaces in WIT via wit-bindgen; mods define systems in WIT and receive Commands; references Bevy 0.19 deps. Rust/Python/Go examples. Roadmap phase 3 = perf.
- Bevy discussion on WASM modding: https://github.com/bevyengine/bevy/discussions/5908
- Hot-reloading Rust instead of scripting (dev-iteration only, not for end-user mods):
  - Bevy 0.17 shipped native `hotpatching` via Dioxus subsecond (PR #19309; https://bevy.org/news/bevy-0-17/). Systems only; binary crate only; no wasm; changing system params breaks reload; run with `dx serve --hot-patch`. Interim crate: TheBevyFlock/bevy_simple_subsecond_system (`#[hot]`, 0.4 → Bevy 0.18). Hotpatched systems run exclusively; struct changes break queries.
  - dexterous_developer (dylib + `reloadable_scope!` + rmp_serde state migration): archived 2026-02-08, last Bevy 0.14. hot_lib_reloader / ridiculous_bevy_hot_reloading: same dylib approach, `#[hot]`.

## 2. Lua runtimes for Rust

- mlua (https://github.com/mlua-rs/mlua, 0.11.x, 0.12 rc): Lua 5.1–5.5, LuaJIT, Luau. `vendored` builds C sources statically. Features: `async` (coroutine-backed futures), `serde` (LuaSerdeExt: to_value/from_value), `send`, `macros`, `module` (build Lua C-modules in Rust), `luau`, `luau-jit`, `luau-vector4`. `Lua::sandbox(true)` (Luau only) enables readonly builtins + per-thread global tables. Limits: `Lua::set_memory_limit` (5.4/Luau, custom allocator), `set_hook(HookTriggers::every_nth_instruction)` for instruction budgets, Luau `set_interrupt`. WASM: `wasm32-unknown-emscripten` only (no JIT), NOT `wasm32-unknown-unknown`. UserData trait with `add_method`/`add_field`/metamethods; very mature ergonomics. Caveat: with PUC Lua, C stdlib functions like string.rep can still blow memory/time despite hooks — Luau's sandbox is the safer choice.
- rlua: deprecated, merged into mlua.
- piccolo (https://github.com/kyren/piccolo, 0.3.3, June 2024, "very experimental"): pure-Rust stackless/trampoline VM on gc-arena; callbacks return `Sequence`s driven by an `Executor` (like Futures). Fuel-based instruction limits and arena-tracked memory → true CPU+RAM sandbox and DoS resilience by design; trivially compiles to wasm32-unknown-unknown. Missing: weak tables/finalizers, most of string/table/io/os stdlib, stack traces, debugger. Not production-ready for modders who expect stock Lua semantics.
- Luau (https://luau.org/sandbox, https://luau.org/performance): Lua 5.1 base + gradual typing, faster interpreter than 5.4, optional native codegen (~1.6x slower than LuaJIT JIT; interpreter roughly on par with LuaJIT interpreter). Sandbox: io/package/most os+debug removed, no `load`/`loadstring`/bytecode loading, readonly builtins, per-script globals, no `__gc` (host tag destructors instead), interrupt callback (Roblox uses 10 s watchdog), pluggable allocator. Shipped in Alan Wake 2, Warframe, Farming Simulator 25, Roblox. Type checker gives modders IDE support (luau-lsp).
- Fennel: Lisp that compiles to Lua; usable on any of the above as a transpile step. Teal: typed Lua → Lua compiler (alternative to Luau for typing on PUC Lua).
- Determinism: PUC Lua/Luau are deterministic except `pairs` order over hash parts and float formatting; LuaJIT differs in number semantics vs 5.3+ integers. For lockstep multiplayer, avoid LuaJIT and iterate sorted keys.

Summary matrix (Lua family):

| Runtime | Perf | Sandbox | wasm32 | Maturity |
|---|---|---|---|---|
| mlua+Lua 5.4 | good | weak (hooks, mem limit) | emscripten only | very mature |
| mlua+LuaJIT | best | weak | no | mature, JIT frozen at 5.1 |
| mlua+Luau | very good (+opt JIT) | strong, designed for UGC | emscripten only | mature (Roblox) |
| piccolo | ok | strongest by design | yes | experimental |

## 3. Alternatives to Lua

- Rhai (https://rhai.rs, 1.25): Rust-native, Rust-like syntax, pure Rust → wasm32-unknown-unknown (<400 KB), rich safety knobs (`set_max_operations`, `on_progress`, `set_max_call_levels`, `max_string_size/array_size/map_size`). ~2x slower than CPython on real workloads; tree-walking. Excellent embedding, weak modder familiarity. Supported by BMS.
- Rune (https://docs.rs/rune, 0.14.2, May 2026): stack VM, Rust-like syntax, async/generators, serde, budget/environment hooks, `rune-wasm` for wasm. Moderate community. BMS support paused.
- Koto (https://koto.dev, 0.16): simple expressive syntax, refcounted (cycles leak), aimed at creative coding/game iteration; small ecosystem.
- Roto (NLnet Labs): compiled (cranelift) typed scripting, fast, newer.
- Steel (https://github.com/mattwparas/steel): embeddable Scheme (R5RS-ish, R7RS in progress), bytecode VM, used in Helix plugin work.
- Mun: no meaningful 2026 activity found; treat as dormant. Dyon: dormant. Gluon: dormant.
- JavaScript: rquickjs (QuickJS bindings, small, sandboxable, wasm-capable), boa (pure Rust, slower, wasm-native), deno_core (V8: fast, huge, no wasm). Punchy precedent above.
- Python: pyo3 (embeds CPython, no sandbox, no wasm), RustPython (pure Rust, slow, incomplete).
- WASM component model: wasmtime (v45) + wit-bindgen; Extism (wasmtime under the hood, PDKs for many languages, "GameBox" game platform uses it). Sandboxing is the strongest of all options (capability-based, fuel, memory limits), language-agnostic, but interop is copy-based (no shared references), tooling is heavy for hobby modders, and debugging is poor. wasvy is the Bevy-specific take.
- Pure data: JSON/RON/TOML "datapacks" (Minecraft datapacks, Vintage Story content mods, Bevy RON scenes/BSN). Zero sandbox concern, zero language learning, but no behaviour.
- Benchmarks: khvzak/script-bench-rs (https://github.com/khvzak/script-bench-rs) compares boa, koto, mlua (5.4, luau), rhai, roto, rquickjs, wasmi, wasmtime on "sort Rust objects" style interop workloads (M5 Max, rustc 1.96). Typical ordering: wasmtime/luau/mlua fastest, rhai and boa slowest; results are images so consult the repo.

Comparison table:

| Lua 5.4 | mlua | high | medium | high | emscripten only | dynamic (Teal opt.) | very high (Roblox/WoW/Factorio/Luanti) |
| LuaJIT | mlua | high | medium | highest | no | dynamic | high |
| Luau | mlua `luau` | high | high | high (+JIT) | emscripten only | gradual | very high (Roblox) |
| Lua (pure Rust) | piccolo | experimental | highest | medium | yes | dynamic | high |
| Rhai | rhai | high | high | low | yes | dynamic | low |
| Rune | rune | medium | medium | medium | yes | dynamic | low |
| Koto | koto | medium | low | medium | yes | dynamic | very low |
| JS | rquickjs / boa / deno_core | high/med/high | med/med/low | med/low/high | no/yes/no | dynamic (TS via transpile) | high |
| Python | pyo3 / RustPython | high/medium | none/low | med/low | no/yes | gradual | high |
| WASM (any lang) | wasmtime+wit-bindgen, Extism, wasvy | high runtime, young game tooling | highest | high (copy interop) | n/a (host) | per language | low (toolchain) |
| Data only | serde RON/JSON/TOML | high | n/a | n/a | yes | schema | high |

## 4. Precedents for scripted, moddable game UIs

### Luanti (Minetest) — string DSL + Lua callbacks
- Formspec (https://api.luanti.org/formspec/): a declarative string DSL, `element[params]` concatenated: `formspec_version[6]size[8,9]list[current_player;main;0,4.85;8,1;]listring[]`. Versions: v1 (padding/spacing quirks), v2 (5.1.0: real_coordinates, `background9[]`), v3 (5.2: draw order), v4 (5.4: dropdown index events), v5 (5.5: `padding[]`), v6 (5.6: 9-slice + animated images), v7 (5.8: focused states, `field_enter_after_edit`), v8+ (scroll container padding, hypertext tooltips).
- Inventory widgets: `list[location;listname;x,y;w,h;start]` with locations `current_player`, `nodemeta:x,y,z`, `player:name`, `detached:name`; `listring[]` chains lists for shift-click transfer; `listcolors[]`, `listimages[]`. Items: `item_image[]`, `item_image_button[]`. Layout: `container[]`, `scroll_container[]`, `tabheader[]`, `style[]/style_type[]` with states (hovered/pressed/focused), `tooltip[]`, `hypertext[]`, `model[]` (3D preview).
- Shown via `core.show_formspec(player, formname, fs)`, node meta `formspec` string, or `player:set_inventory_formspec()`. Input returns as a flat table in `core.register_on_player_receive_fields(func(player, formname, fields))` / node `on_receive_fields`. The whole screen is re-sent as a string on every change; there is no retained tree, no events except field submit. `InvRef` (`get_list`, `set_stack`, `add_item`, `room_for_item`) plus node callbacks `allow_metadata_inventory_move/put/take` mediate inventory rules.
- Registries: `core.register_node/craftitem/tool("modname:name", def)`, `core.register_craft({output=..., recipe={{...}}})`, `register_craft_predict`, `core.get_all_craft_recipes(item)` powers guides. Mods have `mod.conf` (name, depends, optional_depends); load order is dependency-sorted.
- Inventory UIs as mods: sfinv (https://github.com/rubenwardy/sfinv) `sfinv.register_page(name, {title, get(self, player, context) -> sfinv.make_formspec(...), on_player_receive_fields})` — tabbed pages contributed by other mods. unified_inventory (https://github.com/minetest-mods/unified_inventory) is effectively NEI: `register_page`, `register_button`, `register_craft_type` (custom recipe kinds, e.g. cooking), search, recipe/usage browsing, click-to-fill crafting grid. i3 is the modern alternative with a richer API.
- HUD API (https://api.luanti.org/hud/): `player:hud_add({hud_elem_type="image"|"text"|"statbar"|"inventory"|"hotbar"|"waypoint"|"image_waypoint"|"compass"|"minimap", position={x,y} 0..1, offset px, alignment, scale, text, number, item, direction, z_index, style})`, `hud_change`, `hud_remove`, `hud_set_flags`, `hud_set_hotbar_itemcount`. Pure data tables — nice model.
- Formspec replacement: issue #6527, PR #12926 → #14263 by v-rob. Retained element tree (Manager/Env/Elem), binary serialization, style-by-ID selectors (universal/type/id/class/state), axis/flex-like layout. Still early, sprint-based. Lesson: the string DSL scaled poorly and they are moving to a retained, styled tree.

### Factorio — imperative tree API + data-stage prototypes
- Data lifecycle (https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html): settings stage (settings.lua / -updates / -final-fixes), data stage (data.lua / data-updates.lua / data-final-fixes.lua) in ONE shared Lua state, run per file-round across all mods; mods ordered by dependency depth then natural sort of name. `data:extend{{type="item", name="x", icon=..., stack_size=50}, {type="recipe", ...}}`. After data stage the state is discarded and prototypes are immutable. Control stage: each mod gets its own Lua VM, `control.lua`, `storage` table (serialized into save), `script.on_event`, `remote.add_interface` for cross-mod calls, migrations (JSON + Lua), `on_configuration_changed`. `info.json` holds name/version/dependencies with `"? optional"`, `"! incompatible"`, `"~ no-order"` prefixes.
- GUI (https://lua-api.factorio.com/latest/classes/LuaGuiElement.html): per-player roots `player.gui.top/left/center/screen/relative`. `parent.add{type="frame", name=..., caption=..., direction="vertical", style="inner_frame"}` returns element; children by name `frame.my_button`; `destroy()`, `clear()`, `style` (LuaStyle or prototype name), `tags` (persisted table for identifying elements in handlers), `drag_target`, `anchor` (relative GUI attached to vanilla GUIs like inventory/crafting, by `gui=defines.relative_gui_type.*`, position). Types: frame, flow, scroll-pane, table, tabbed-pane, textfield, text-box, slider, drop-down, list-box, checkbox, radiobutton, button, sprite-button, choose-elem-button (elem_type item/entity/fluid/recipe/signal/technology/… → item picker), sprite, label, progressbar, minimap, camera, entity-preview, switch, inventory. Events are global per mod: `on_gui_click`, `on_gui_text_changed`, `on_gui_elem_changed`, `on_gui_closed`, `on_gui_selection_state_changed` with `event.element`. Styles are prototypes in `data.raw["gui-style"].default` (`type="frame_style", parent="frame", padding=...`), defined at data stage; FFF-174 covers mod-gui. State does not replicate; each player has own tree. Cannot keep Lua references across save/load → tags/names idiom.
- Recipe browsers: FNEI (NEI clone), Recipe Book by raiguard (https://codeberg.org/raiguard/RecipeBook, "modern FNEI"), and since 2.0 the built-in Factoriopedia (FFF-397, https://www.factorio.com/blog/post/fff-397) — evidence that a first-party "recipe explorer" is expected.

### World of Warcraft — XML + Lua (FrameXML)
- https://warcraft.wiki.gg/wiki/XML_user_interface, https://warcraft.wiki.gg/wiki/Secure_Execution_and_Tainting. `.toc` manifest lists files/deps/saved variables. XML `<Ui>` root; widgets `<Frame>`, `<Button>`, `<Texture>`, `<FontString>`, `<Anchors><Anchor point="TOPLEFT" relativeTo="$parent" x= y=/></Anchors>`, `<Size>`, `<Layers level="ARTWORK">`, templates via `virtual="true"` + `inherits=`, `$parent` naming, `mixin=`. `<Scripts><OnLoad>/<OnEvent>/<OnClick>`. Since 1.10 Lua `CreateFrame("Frame", name, parent, template)` + `frame:SetScript("OnEvent", fn)`, `frame:RegisterEvent("PLAYER_LOGIN")`, `SetPoint`. Taint model: execution starts secure; touching addon-created data taints it; protected functions (CastSpell, targeting) refuse tainted callers; SecureTemplates/secure handlers let addons drive protected actions declaratively via attributes. 20 years of addon ecosystem (ElvUI, WeakAuras) proves XML+Lua retained-tree UI scales, and demonstrates a permission model for scripted UIs.

### Others (brief)
- Garry's Mod Derma: imperative Lua VGUI: `local f = vgui.Create("DFrame") f:SetSize(300,200) f:MakePopup()`; `DButton.DoClick = function() end`; `Paint` override hook per panel. https://wiki.facepunch.com/gmod/Derma_Basic_Guide
- Roblox: Luau, Instance tree `Instance.new("Frame").Parent = screenGui`; `UDim2` (scale+offset), `AnchorPoint`, `ZIndex`, `AutomaticSize`, layout constraint children (`UIListLayout`, `UIGridLayout`, `UIPadding`, `UIAspectRatioConstraint`); events `Activated`, `InputBegan`, `MouseEnter`. https://create.roblox.com/docs/reference/engine/classes/GuiObject
- Don't Starve (Together): Lua `Class(Widget)` tree with `AddChild`, `SetPosition`, `SetScale`; mods subclass widgets and hook screens (`AddClassPostConstruct`). Noita: immediate-mode Lua GUI (`GuiCreate`, `GuiButton(gui, id, x, y, text)`, `GuiImage`) called every frame. Project Zomboid: Kahlua (Lua 5.1 on JVM) with `ISUIElement`/`ISPanel` class hierarchy exposing Java. Starbound: JSON `.config` panes (`"gui": {widgets...}`) with `"scripts": [...]`, `"scriptWidgetCallbacks": ["sayhello"]`; widgets call named Lua functions; ScriptCanvas for custom drawing. Vintage Story: content mods = JSON assets (blocks/items/recipes, JSON patching), code mods = C# `GuiDialog` + `GuiComposer` fluent builder; libGUI community alternative. tModLoader: C# `UIState`/`UIElement`/`UserInterface` retained tree. RimWorld: C# Harmony patches + XML Defs + `Widgets.*` immediate mode. DFHack: Lua `gui.widgets` retained widgets over Dwarf Fortress. Balatro/LÖVE: Lua table-based "UIBox" definitions (`{n=G.UIT.R, config={...}, nodes={...}}`) — a pure data-table UI tree in Lua, worth noting.

### Which model fits ECS + modders
- String DSL (formspec): easiest to transmit and to generate from any language, but no retained state, poor error reporting, no events beyond submit; Luanti itself is abandoning it.
- Imperative tree (Factorio/Derma/Roblox): most familiar to modders, natural with per-player GUIs, but forces scripts to hold handles and hand-write layout; maps to Bevy entities 1:1 (each element = entity with Node components) if handles are `Entity` ids stable across frames.
- XML/data + Lua hooks (WoW, Starbound, Balatro): declarative layout as data, behaviour as named callbacks. Fits ECS best: a UI definition (RON/JSON/Lua table) is a scene/BSN-like template spawned into entities; callbacks are strings resolved to script functions; templates/inherits map to prefabs.
- Recommendation: hybrid — data-defined screens (Lua tables or RON) + imperative escape hatch for dynamic content (recipe lists), Factorio-style `tags` on elements, and `anchor`/relative-GUI slots so overlay plugins (NEI-style) can attach to vanilla screens without owning them.

## 5. Modding architecture patterns
- Manifests: `mod.toml`/`info.json`/`mod.conf` with id, version (semver), `api_version`, dependencies with ranges and ordering (`before/after/none`, `? optional`, `! incompatible`). Topological sort by deps then stable name sort (Factorio). Cycles = hard error.
- Namespaced IDs: `modid:item_name` (Minecraft `ResourceLocation`, Luanti, Factorio names by convention). Interning to `u32`/`RegistryId` at freeze; keep string→id map for scripts and data.
- Two-stage lifecycle: definition/data stage (registries open, mods run `data.lua`, patches applied in rounds: base → updates → final-fixes) then FREEZE (NeoForge `RegisterEvent` then frozen registries; Factorio immutable prototypes). Runtime/control stage: separate script contexts per mod, event subscriptions, per-mod persistent `storage`. In Bevy: data stage runs in a `Startup`/`ModLoad` state before `PreUpdate` systems; registries as Resources with a `Frozen` marker; runtime scripts attach via BMS `StaticScript`.
- Registries as plugin points: items, blocks, recipe types (`register_craft_type` à la unified_inventory: name, description, icon, width/height, how to resolve inputs→outputs), GUI screen types, tooltip providers, tabs/pages. Data maps (NeoForge "data maps") for attaching mod data to others' entries.
- Event bus ↔ Bevy: Bevy `Message`s (formerly Events) + Observers (`On<Pointer<Click>>`, custom `On<SlotClicked>`) are the natural bus. Expose to scripts as BMS callback labels: `on_slot_click(entity, slot_ix, button, modifiers)`, `on_gui_closed`, `on_recipe_lookup(item_id) -> [recipes]`. Scripts return data (tables) not handles.
- Declaring UI as data from Lua: a Lua table `{type="frame", id="chest", size={176,166}, children={{type="slot_grid", inventory="block", cols=9, rows=3, pos={8,18}}, {type="player_inventory", pos={8,84}}}}` → serialized via mlua serde to a Rust `UiNodeDef` enum → spawned as entities (Node/UiImage/9-slice, `SlotGrid` components). Events flow back via element `tags` + callback names (Starbound `scriptWidgetCallbacks`, WoW `<OnClick>`). RON files can express the same tree for no-script mods; BSN (Bevy's upcoming scene notation) is the long-term native fit.
- Capabilities/components: item behaviour via components on item-stack entities or via "capability" traits registered by mods (NeoForge capabilities). Scripts add reflected dynamic components (BMS `register_new_component`) for mod-private data.
- API versioning: version the script API separately (`api_version = 1`), keep generated docs (BMS can emit LSP/ldoc files), deprecate with shims. Stable ABI is impossible for Rust dylibs → scripts/WASM are the only stable-ABI path.
- Sandboxing/permissions: tiers — data-only mods (safe), scripted UI mods (Luau sandbox, no io/os, memory + interrupt limits), trusted native plugins (Rust crates compiled in). WoW-style protected operations: scripts request actions (e.g. move stack) through validated commands, never mutate inventories directly — the server/authority validates like Luanti `allow_metadata_inventory_*`.
- Hot reload during dev: Bevy asset watcher for scripts and RON UI defs; subsecond for Rust systems; keep UI defs as assets so redefinition re-spawns screens.

## 6. Localization and resource packs
- bevy_fluent 0.15.0 (2026-06-22, Bevy 0.19): Project Fluent `.ftl` bundles loaded as assets, locale negotiation. https://lib.rs/crates/bevy_fluent ; upstreaming analysis discussion https://github.com/bevyengine/bevy/discussions/11277. es-fluent-manager-bevy: `.ftl` via AssetServer, hot reload, `FluentText` component auto-refresh. bevy_simple_i18n wraps rust-i18n but embeds locales at compile time (bad for mods). Recommendation: Fluent keys namespaced `modid.item.name`, each mod ships `locale/<lang>.ftl`, layered by load order (Minecraft lang JSON model).
- Asset layering: Bevy Multiple Asset Sources (PR #9885): `app.register_asset_source("mods", AssetSourceBuilder::platform_default("mods", None))`, custom `AssetReader` wrapping the default (`examples/asset/custom_asset_reader.rs`) to implement an overlay/chain reader that checks resource packs → mods (reverse load order) → base. Caveats: folder loading only from primary source (issue #10120); GLTF sub-assets with custom sources (#10903). Texture atlases for GUI: resource packs override `modid:textures/gui/chest.png`; use a `PackLayers` resource rebuilt on pack change, and 9-slice `ImageNode` with `TextureSlicer` for scalable GUI panels.

## Key takeaways for a Bevy plugin set
1. Pick Lua, specifically Luau through mlua (`luau` feature, `Lua::sandbox(true)`, interrupt + memory limit) as the modder-facing language: maximum familiarity (Roblox/WoW/Factorio/Luanti), strong UGC sandbox, gradual typing for IDE support. Offer Lua 5.4 as an alternate feature for purists; skip LuaJIT for determinism.
2. Embed via bevy_mod_scripting rather than rolling your own: reflection-driven bindings, hot reload, callback labels, per-script contexts, dynamic components. Budget for Bevy-version lag and no wasm. Keep a thin trait layer so bevy_scriptum or a WASM backend could be swapped later.
3. Do not expose raw ECS queries to mods as the primary API. Publish a curated, versioned "modding API" namespace (items, inventories, recipes, screens, tooltips) registered with `NamespaceBuilder`; reserve raw `world` access for trusted/dev mods.
4. Split definitions from behaviour Factorio-style: a data stage (RON/JSON/TOML or Lua tables returning data) that fills registries, then FREEZE, then a control stage where scripts only react to events. This makes data-only mods possible and keeps recipe/item lookups (NEI) pure and cacheable.
5. Namespaced string IDs (`modid:name`) everywhere in data and scripts; intern to numeric ids at freeze; never expose Entity ids as persistent identifiers.
6. Define screens as data trees (RON asset or Lua table → serde → `UiNodeDef`), spawned into Bevy UI entities; support `inherits` templates (WoW) and named slots/anchors (Factorio `gui.relative` + `anchor`) so overlay plugins attach to vanilla screens.
7. UI events flow back as typed messages/observers translated into BMS callbacks with element `tags`; scripts handle `on_slot_click`, `on_gui_closed`, `on_search_changed`, and respond with commands, not direct mutation.
8. Model inventories as Luanti does: lists + `listring`-style shift-click transfer rules + `allow_*` validation hooks that scripts can override; server/authority validates every move.
9. Make "recipe type" a first-class registry (unified_inventory `register_craft_type`) so NEI-style browsers enumerate arbitrary mod machines; provide `get_all_craft_recipes(item)` and `get_usages(item)` as API primitives and a built-in Factoriopedia-like browser plugin.
10. Version the script API independently (semver `api_version` in `mod.toml`), generate LSP/type stubs (luau-lsp `.d.luau`) from the registry, and ship deprecation shims.
11. Load order: dependency-topological then stable alphabetical; manifest supports optional/incompatible/ordering hints; cycles fail loudly.
12. Assets: a chained/overlay `AssetReader` across base → mods → resource packs; textures and `.ftl` locale files both resolved through it; 9-slice GUI textures so packs can retheme without code.
13. Localization via Fluent (bevy_fluent or es-fluent-manager-bevy), keys namespaced per mod, hot-reloadable.
14. Use Bevy 0.17+ subsecond hotpatching plus asset-watched scripts/RON for developer iteration; do not treat Rust dylib hot reload as a modding surface (dexterous_developer is archived; no stable ABI).
15. Keep the door open for WASM (wasvy / wasmtime component model) as a "power mod" tier later: same registry + event API expressed in WIT, but do not make it the entry-level modding story yet — tooling is too heavy for hobby modders.
