# Recipe/item viewer overlays in Minecraft modding: NEI -> JEI -> REI/EMI (research report)

Primary sources were read directly from the current API source trees (JEI branch 1.21.1, REI default branch, EMI branch 1.21, Jade, Mouse Tweaks) plus mod pages and historical forum mirrors. Where a claim is from a secondary page, the URL is given. Fandom (FTB wiki) pages returned HTTP 402/403 and could not be used.

## 1. History and evolution

**TooManyItems (TMI), Marglyph, ~2011 (first version for Beta 1.2).** An inventory editor: a full item list drawn next to the inventory, click to spawn, plus save/load inventory states, time/rain/gamemode buttons. No recipe viewing. Copyright notes "2011-2014 by Marglyph". (https://mcarchive.net/mods/toomanyitems, https://www.minecraftforum.net/forums/mapping-and-modding-java-edition/minecraft-mods/1272385-toomanyitems-the-inventory-editor-and-more-1-8)

**Recipe Book (Risugami), Craft Guide.** Recipe-only browsers; Craft Guide arrived around the same time as NEI.

**Not Enough Items (NEI), chicken_bones, first release 02 Nov 2011 (v1.0.3 for MC 1.0.0).** chicken_bones: "Alexandria and a few others on the IRC suggested that I merge both Too Many Items and Recipe Book to remove their greatest flaws, ironically too many items, or in the case of recipe book, too many recipies." and "Too Many Items was great, the one thing it lacked was an easy way to search and sort your items." Key UX it introduced: R (recipes) / U (uses) while hovering; Backspace to go back; a bottom search box with `*`/`?` wildcards and Java regex ("Bl?ck" matches Black/Block), case-insensitive, right-click to clear; "Item Subsets" dropdown (right-click hides a set, double-click shows only that set, shift-click types `@setname` into the search); Recipe Mode vs Cheat Mode ("for playing legit and just using the recipe book component"); utility buttons: Creative/gamemode toggle (C), Rain toggle, Magnet mode ("any items within a reasonable distance will pick themselves up and fly towards you"), four Time buttons (Dawn/Noon/Dusk/Midnight, forward only), Heal, Trash (click deletes held item, shift-click deletes all of that type, shift-click empty clears inventory, plain click toggles Trash Mode); X = enchantment selector honoring conflict rules; 7 named inventory save states; "SHIFT+placing items in containers moves all inventory items of that type"; server side `NEIServer.cfg` with per-player permissions and a banned-blocks list. Addon API: mods ship a class named `NEI****Config` implementing `IConfigureNEI`, discovered ModLoader-style, with the rule "Your mod must not directly call any NEI functions or classes as that will make it dependant on NEI to function." Recipe handlers extended `TemplateRecipeHandler`. NEI was a coremod (CodeChickenCore) and used lots of bytecode patching. (https://overminddl1.com/minecraft/sites/ChickenBonesMods.html, https://github.com/Chicken-Bones/NotEnoughItems)

**Just Enough Items (JEI), mezz, 2015 for MC 1.8.** README states the thesis: "an Item and Recipe viewing mod for Minecraft with a focus on stability, performance, and ease of use. This means: just items and recipes; clean API for developers; not a coremod – no dependencies other than Forge." NEI's 1.8+ port became an addon that requires JEI, which is effectively how JEI replaced it: the coremod/ASM approach broke every version, while JEI was pure-API Forge with a stable plugin interface, so mod authors integrated with JEI and NEI's user base followed. The cheaty "utilities" (rain/time/heal/magnet) were dropped; only cheat mode, edit/hide mode and bookmarks survived. (https://github.com/mezz/JustEnoughItems, https://www.curseforge.com/minecraft/mc-mods/notenoughitems)

**Had Enough Items (HEI), CleanroomMC/Rongmario.** 1.12.2-only JEI fork: memory/load-time/render optimizations, overhauled bookmarks and autocrafting, reorderable bookmarks, diacritic-aware search, choosing default fluid containers when picking fluids from the list. (https://www.curseforge.com/minecraft/mc-mods/had-enough-items)

**Roughly Enough Items (REI), shedaniel, 2018+.** Started as the Fabric answer when JEI was Forge-only; "a clean and customizable alternative to JEI". Different vocabulary: `EntryStack` (typed ingredient), `Display` (a recipe), `DisplayCategory`, `OverlayDecider`, favorites with pluggable `FavoriteEntryType` (favorites can be things other than items, e.g. game-mode/weather/time toggles), collapsible entries in the panel, "input methods" (e.g. pinyin search), configurable search argument types including regex `r/…/`. (https://modrinth.com/mod/rei, https://github.com/shedaniel/RoughlyEnoughItems)

**EMI, Emily Ploszaj, 2022+.** Self-description: "a featureful and accessible item and recipe viewer" that "brings many new features, and optimizes for the user experience." Philosophy points from its mod page: "Zero third party dependencies. EMI only requires standard, first party Fabric/Quilt APIs"; "A clean and modern API, built from the ground up to be simple, powerful, and suit all of EMI's features"; runtime JEI compat ("install JEI alongside EMI and they will work together to share recipes", JEI's GUI is hidden). Distinctive features: **recipe tree** ("breaking down the cost of a complex craft, showing you every step", with base ingredient totals and leftovers); **craftable mode** (sidebar shows only what you can craft from your inventory; toggled or bound to empty search); **favorites for recipes as well as items**, usable "to quickly craft at a button press"; **synthetic favorites** generated from a tree so you can "craft every step for exactly as much as you need"; **recipe defaults** (which recipe a tree should expand an item through; shipped as `assets/emi/recipe/defaults/<modid>.json` with an `added` array of recipe ids, authored in-game via dev mode and exported from `emi.json`); **quick-craft binds** straight to inventory or cursor; smart tag display with translations. Note: EMI does still have cheating (`general.cheat-mode` = true/false/creative, binds `cheat-one-to-inventory`, `cheat-stack-to-cursor`, `delete-cursor-stack`), so "no cheating features" is not accurate; what EMI dropped is the NEI-style world utilities. It also has sidebar page types INDEX, CRAFTABLES, FAVORITES, LOOKUP_HISTORY, CRAFT_HISTORY, and even CHESS. (https://modrinth.com/mod/emi, https://www.curseforge.com/minecraft/mc-mods/emi, https://github.com/emilyploszaj/emi/wiki/Recipe-Defaults, EmiConfig.java)

## 2. UX catalogue (with concrete key/config facts)

- **Side item panel** with paging (JEI: `previousPage`/`nextPage` mappings, wheel scroll) and a grid whose column/row count derives from free screen space beside the container. EMI has four sidebars (left/right/top/bottom), each with configurable page lists, max size in columns/rows and margins (`ui.left-sidebar-size`, `ui.left-sidebar-margins`). JEI has a "center search bar" option (`centerSearch`); EMI `ui.center-search-bar`.
- **Search box syntax.** JEI 1.21 (ElementPrefixParser.java): unprefixed = display names; `@` mod name; `#` tags; `$` tooltips; `%` creative tab; `^` color; `&` resource id. Each prefix has a mode ENABLED / REQUIRE_PREFIX / DISABLED (defaults: tooltips ENABLED so plain words also hit tooltip text; mod names and tags REQUIRE_PREFIX; color, id, creative tab DISABLED). Tokenizer: whitespace splits terms (AND), `-` at token start negates, `"quoted phrases"`, `\` escape; older JEI versions used `|` for OR ("tool|axe"). Beware the prefix drift: in NEI/old JEI `#` was tooltip and `$` was OreDict; JEI now swapped them; REI uses `@` mod, `$` tag, `#` tooltip, `*` identifier, `r/regex/`; EMI uses `@` mod, `#` tag, `$` tooltip, `/regex/`, `"quoted"`, `|` OR, `&` AND (parsed, implicit), and `-` negation (EmiSearch.TOKENS regex). EMI also has `search-tooltip-by-default`, `search-mod-name-by-default`, `search-tags-by-default` toggles and colors each prefix differently in the text field. AE2 terminals copied the same grammar (`@` mod, `$` tooltip, `*` id, `#` tag, `|` OR) and offer "Remember last search", "Auto-Focus on open", "Sync with JEI/REI search". (https://deepwiki.com/AppliedEnergistics/Applied-Energistics-2/5.4-search-and-filtering-system)
- **Hover keys.** JEI defaults: R show recipes, U show uses, A bookmark, Ctrl+O toggle overlay, Ctrl+F focus search, Up/Down search history, Backspace recipe back, PgUp/PgDn recipe pages, Shift+PgUp/PgDn category, hold Shift pauses ingredient cycling, Esc closes. Cheat mode toggle via Ctrl+click on the config wrench; edit mode with `toggleHideIngredient` and `toggleWildcardHideIngredient` (hide one variant vs all subtypes). EMI adds: view-stack-tree, view-tree, favorite, default-stack, craft-one/craft-all, craft-one-to-inventory, craft-all-to-inventory, craft-one-to-cursor, show-craft, copy-recipe-id, hide-stack / hide-stack-by-id (edit mode).
- **Bookmarks/favorites panel** on the opposite side; JEI options `addBookmarksToFrontEnabled`, `bookmarkOutputAsRecipe` (bookmark a whole recipe, not just its output), `dragToRearrangeBookmarksEnabled`, `holdShiftToShowBookmarkTooltipFeatures`, plus `transferRecipeBookmark`/`maxTransferRecipeBookmark` (craft a bookmarked recipe directly from the bookmark). REI favorites are typed (`FavoriteEntryType` registry, serialized as NBT with a `type` key).
- **Recipe screen**: category tabs (crafting, smelting, brewing, anvil, smithing, stonecutter, campfire, "information", plus mod categories), recipe catalysts (workstations) shown beside recipes, ingredient cycling for tag inputs, focus highlighting of the ingredient you searched from, per-recipe `+` transfer button. JEI transfer results: null = success, else `IRecipeTransferError` which renders red highlights over missing slots and a tooltip; `maxTransfer` (shift-click) moves as many sets as possible; `doTransfer=false` is the dry-run used for button state. REI returns `Result.createFailed(Component)` with a translucent red color 0x67ff0000 painted over the recipe. EMI's `StandardRecipeHandler` needs only `getInputSources`, `getCraftingSlots`, optional `getOutputSlot`, and derives canCraft/craft; EMI counts "cost per batch" on hover.
- **Ghost items**: JEI `IGhostIngredientHandler` lets a mod accept an item dragged from the list into a filter slot "for setting recipes or anything else that does not need the real ingredient to exist"; REI has `DraggableStackProvider/Visitor` on `ScreenRegistry`; EMI `EmiDragDropHandler`.
- **Cheat mode**: server-authoritative. JEI `ServerCommandUtil.hasPermissionForCheatMode` passes if the player is creative, has op permission level, or may run `/give`; otherwise sends `PacketCheatPermission(false)` back so the client disables the mode. `giveMode` = INVENTORY or MOUSE_PICKUP; `cheatToHotbarUsingHotkeysEnabled` puts the item on a hotbar number key.
- **Item hiding/blacklist**: JEI "edit mode" writes hidden UIDs to a config; `showHiddenIngredients` debug toggle; REI `BasicFilteringRule`; EMI `dev.edit-mode`, plus resource-pack driven `removeEmiStacks` filters for packs.
- **Utility buttons** were NEI-only (rain, time x4, heal, magnet, gamemode, trash, enchant, potions, save states). REI keeps a small subset as favorites-panel toggles (gamemode/weather/time) and shows why: they belong in a per-player "favorites" region, not the item list.
- **Exclusion zones / extra areas**: every viewer asks the current screen for rectangles it must not draw over (side tabs, JEI's `getGuiExtraAreas`, REI `ExclusionZones`, EMI `EmiExclusionArea`). JEI draws a shadow texture (`exclusion_area_shadow.png`) and even has a debug handler; EMI has `dev.highlight-exclusion-areas`.
- **Tooltips**: mod name appended to tooltips (JEI does this; EMI `ui.mod-name-tooltip` with a fallback flag "in case another mod provides behavior"); vanilla F3+H "advanced tooltips" shows id/NBT/durability and JEI's `searchAdvancedTooltips` lets you index those strings. JEI adds tag-content tooltips (`tagContentTooltipEnabled`, hide when a tag has a single member), creative tab names, and a "Recipe By <mod>" line.
- **Keyboard focus**: the overlay's text field must not steal keys when the container's own field is focused (AE2 issue 6200: terminal auto-focus overriding the JEI search bar); JEI exposes `hasKeyboardFocus()` on `IIngredientListOverlay` and `IJeiKeyMappings` so other mods can honor the same binds.

## 3. Plugin / extension API design

**JEI (`IModPlugin`, discovered via `@JeiPlugin` annotation scan, must return a unique `ResourceLocation` plugin id).** Lifecycle order (IModPlugin.java): `configureJei` (early feature flags such as disabling the GUI) → `registerItemSubtypes` / `registerFluidSubtypes` (`ISubtypeInterpreter.getSubtypeData(ingredient, UidContext)` returns an equals/hashCode-able object: which NBT/components make a distinct list entry vs. ignored charge/damage) → `registerIngredients` (custom `IIngredientType<T>` + `IIngredientHelper<T>` giving display name, uid, grouping uid, mod id, tags, colors, error info + `IIngredientRenderer`) → `registerExtraIngredients` → `registerIngredientAliases`, `registerAdvancedSearch`, `registerModInfo` → `registerCategories` (`IRecipeCategory<T>`: `getRecipeType`, `getTitle`, `getIcon` (16x16), `getWidth/Height`, `setRecipe(IRecipeLayoutBuilder, T, IFocusGroup)` which places slots with roles INPUT/OUTPUT/CATALYST/RENDER_ONLY and "invisible ingredients" for lookup only, `createRecipeExtras` for per-recipe widgets/input handlers, `draw`, `getTooltip`, `onDisplayedIngredientsUpdate`) → `registerVanillaCategoryExtensions` → `registerRecipes` → `registerRecipeTransferHandlers` (simple `IRecipeTransferInfo` with slot lists, or full `IRecipeTransferHandler` keyed by container class + optional `MenuType` + `RecipeType`) → `registerRecipeCatalysts` → `registerGuiHandlers` (`IGuiHandlerRegistration`: `addGuiContainerHandler`, `addGuiScreenHandler` for non-container screens via `IGuiProperties` (guiLeft/Top/XSize/YSize/screenWidth/Height), `addGlobalGuiHandler`, `addRecipeClickArea` (click the furnace arrow to open smelting recipes), `addGhostIngredientHandler`) → `registerAdvanced` → `registerRuntime` → `onRuntimeAvailable(IJeiRuntime)`, `onRuntimeUnavailable` on logout, `onConfigManagerAvailable`. Ordering: the loader sorts so the vanilla plugin and JEI internal plugin run first. `IGuiContainerHandler` supplies `getGuiExtraAreas`, `getClickableIngredientUnderMouse` (items in non-slot widgets, fluids in tanks), `getGuiClickableAreas`. `IJeiRuntime` exposes `IRecipeManager`, `IRecipesGui`, `IIngredientFilter` (set/get filter text, filtered ingredients), `IIngredientListOverlay`, `IBookmarkOverlay`, `IIngredientManager`, `IIngredientVisibility`, `IJeiKeyMappings`, `IScreenHelper`, `IRecipeTransferManager`, `IEditModeConfig`, config manager. Search storage is pluggable (`ISearchStorage` / `ISearchStorageBuilderFactory` in the API).

**REI (`REIClientPlugin`, extends a generic `REIPlugin` with a provider class; there is also a common/server plugin).** Registration methods: `registerEntryRenderers`, `registerCategories(CategoryRegistry)`, `registerDisplays(DisplayRegistry)` (with `registerRecipeFiller` to auto-convert vanilla recipe types), `registerScreens(ScreenRegistry)`, `registerExclusionZones(ExclusionZones)`, `registerEntries(EntryRegistry)`, `registerBasicEntryFiltering`, `registerCollapsibleEntries`, `registerFavorites(FavoriteEntryType.Registry)`, `registerTransferHandlers`, `registerConfigAddons`, `registerInputMethods`. Ingredient model: `EntryStack<T>` = pair of `EntryDefinition<T>` and value; `EntryDefinition` gives value class, `EntryType`, `EntryRenderer`, identifier, containing namespace, comparator; `EntryIngredient` = list of alternative stacks (a tag slot). `Display` has input/output `EntryIngredient` lists and a `DisplaySerializer` so displays can be sent/saved. `DisplayCategory<T>`: identifier, title, icon `Renderer`, `setupDisplay(display, bounds) -> List<Widget>` (widget-tree UI instead of draw callbacks), fixed display height (default 66) and per-display width (default 150), displays-per-page, optional display merger. `ScreenRegistry`: `registerDecider(OverlayDecider)` where deciders are priority-sorted and answer `isHandingScreen`, `shouldScreenBeOverlaid`, `isInZone(mouse)`, `shouldRecalculateArea`, and can supply an `OverlayRendererProvider`; `DisplayBoundsProvider` gives the container rectangle; `getOverlayBounds(DisplayPanelLocation, screen)`; `registerFocusedStack`; draggable stack/component providers and visitors with priorities. `TransferHandler`: priority, `checkApplicable(Context)`, `handle(Context)` with `isActuallyCrafting()` dry-run flag, results Successful / NotApplicable / Failed(Component, color). Search is argument-type based (`ArgumentType` with prefix, `MatchType`, inverted form `-@mod` or `@-mod`), split on `|` first then quoted/whitespace terms, with an `ArgumentCache`.

**EMI (`EmiPlugin` found through an `@EmiEntrypoint`/loader entrypoint, plus `EmiInitRegistry` for early hooks).** `EmiRegistry` (EmiRegistry.java): `addCategory`, `addWorkstation(category, stack)`, `addRecipe`, `addDeferredRecipes` ("reliant on a majority of EMI metadata" being populated), `removeRecipes(predicate|id)`, `addEmiStack`/`addEmiStackAfter`, `removeEmiStacks`, `addExclusionArea(screenClass, area)` / `addGenericExclusionArea`, `addDragDropHandler`, `addStackProvider` (what stack is under the mouse on a given screen class), `addScreenBoundsProvider`, `setDefaultComparison(key, Comparison)` (NBT/component comparison policy per item, the ISubtypeInterpreter analogue), `addAlias`, `addRecipeHandler(screenHandlerType, handler)`, `addRecipeDecorator`, `getRecipeManager`, `isStackDisabled`. `EmiRecipe`: `getCategory`, `getId` (may be synthetic), `getInputs`/`getCatalysts`/`getOutputs` (inputs indexed as "uses", outputs as "sources"), `getDisplayWidth` (134 px fits the default panel, 160 without tree buttons), `getDisplayHeight`, `addWidgets(WidgetHolder)`, `supportsRecipeTree`, `hideCraftable`, `getBackingRecipe`. `EmiIngredient` is the tag/alternatives abstraction over `EmiStack` (item, fluid, or custom), with amount and chance. EMI renders with a batched renderer (`ui.use-batched-renderer`, "Batching is faster, but may have incompatibilities").

**Lessons for a Rust/ECS plugin API.** (a) Separate *registration phases* with a fixed order (subtypes → ingredient types → categories → recipes → transfer → gui handlers → runtime), because later phases validate against earlier ones. (b) Make the ingredient a *typed, comparable key* (type id + value + a pluggable "subtype/comparison" function) rather than an item stack; fluids, energy, tags, and "info" entries all flow through the same registries and search index. (c) Recipes are *data + a layout builder*: roles (input/output/catalyst/render-only), positions, tooltips callbacks; the viewer owns hit-testing, cycling, focus highlighting and bookmarking so plugins do not. (d) Screen integration is *registry-of-handlers keyed by screen type* with a priority order: bounds provider, exclusion areas, clickable areas, stack-under-mouse provider, drag-drop acceptor, transfer handler. (e) Transfer handlers get a dry-run flag and return structured errors so the UI can paint missing slots. (f) Expose a runtime object (filter text, visible ingredients, bookmarks, key mappings) so other mods can synchronize with the overlay, as AE2 does.

## 4. Integrating with arbitrary container screens

JEI hooks (GuiEventHandler.java): `onGuiInit(screen)` recomputes exclusion areas and layout when a screen opens or resizes; `drawForScreenBackground` "Draws the JEI overlay backgrounds before the screen contents are drawn"; `drawForScreenForeground` "after the screen contents and before deferred tooltips are extracted"; input layers are updated before the screen renders its tooltip; a `drawPostForeground` pass draws clickable-area tooltips only if the mouse is not over a JEI input layer. On Fabric, JEI publishes its own events (`JeiScreenEvents.DRAW_BACKGROUND`, `DRAW_FOREGROUND`, `ALLOW_TOOLTIP`, `ALLOW_MOUSE_DRAG`) because vanilla lacks them; on Forge it uses `ScreenEvent.Render.Post` and tooltip events. The resulting z-order is: screen background → overlay backgrounds → container contents → overlay foreground (items, bookmarks) → container's carried item and deferred tooltips → overlay tooltips. Screen geometry comes from `IGuiProperties` (gui rect + screen size), cached in `GuiPropertiesCache` and refreshed "if dirty"; a layout object crops the display area to the left/right of the container, inserts the search field (`SEARCH_HEIGHT`), the config button, and an optional "lookup history" strip. REI instead asks a priority list of `OverlayDecider`s for the container bounds and `getOverlayBounds(location, screen)`, and re-lays out when a decider says `shouldRecalculateArea`. GUI scale is handled implicitly since all coordinates are in scaled GUI units; EMI's recipe screenshot feature exposes a separate `recipe-screenshot-scale`. Mouse handling is layered: the overlay consumes clicks inside its rectangles first, then passes through; drag from the overlay onto a screen consults ghost-ingredient / drag-drop handlers.

## 5. Performance and indexing

- JEI builds the list once per world join ("Adding N ingredients" / "Added N ingredients" log lines), creating a `ListElementInfo` per typed ingredient with precomputed lowercase names, mod names (id, display name, aliases, optional short names), tag strings, tooltip strings, creative tab names, colors, resource id. Subtype interpreters decide which NBT variants become separate entries; `hasSubtypes` is "an optimization to skip some processing for ingredients that never have subtypes"; `getGroupingUid` (wildcard id) groups variants for hide-all and tag matching.
- Index: one `ISearchStorage` per prefix. The default is a generalized suffix tree (mezz's own `net.mezzdev.suffixtree.GeneralizedSuffixTree`) so any substring matches in O(query length). Low-cardinality prefixes (mod names, tags, creative tabs, colors) are wrapped in a `LimitedStringStorage` that maps each distinct string to one entry set instead of inserting per element. There is also a `BakedSubstringIndex` storage and a `lowMemorySlowSearchEnabled` fallback (`ElementSearchLowMem`, linear scan). Query evaluation: tokens → per-token result sets → intersection for AND, set difference for `-` tokens → sort by configurable stages (ALPHABETICAL, CREATIVE_MENU, INGREDIENT_TYPE, MOD_NAME, TAG, ARMOR, MAX_DURABILITY) → cache the resulting list until filter text, hidden state or visibility changes (`invalidateCache`). Historical issue #1300 documents the long "Building ingredient filter" phase that motivated the async-load branches. (https://github.com/mezz/JustEnoughItems/issues/1300)
- REI caches per-argument results (`ArgumentCache`, `IndexSet`) and runs search asynchronously; EMI runs the search on a daemon `searchThread` and swaps results in when done, and batches item rendering.
- Rendering: only the visible page of the grid is drawn; item icons are baked models rendered through the game's item renderer, so the cost is per visible slot, not per indexed item. Tooltips are built lazily on hover. Large kitchen-sink packs reach tens of thousands of list entries once NBT subtypes (enchanted books, potions, tools with tiers) are expanded, which is why subtype interpreters and the "hide by wildcard" grouping exist.

## 6. Related overlays and inventory helpers

- **WAILA → HWYLA (TehNut) → Jade (Snownee).** HUD tooltip for the block/entity under the crosshair. Jade API: `IWailaPlugin` with `register(IWailaCommonRegistration)` (server side) and `registerClient(IWailaClientRegistration)`; providers are `IComponentProvider<BlockAccessor>` / entity variants registered per block/entity class, `IServerDataProvider` appends NBT that Jade syncs to the client (`appendServerData`, `shouldRequestData`), and every provider has an `Identifier` so the config screen can toggle it; plugins register typed config keys (`addConfig(Identifier, bool|enum|int|float|string)`). (https://github.com/Snownee/Jade, https://jademc.readthedocs.io)
- **Inventory Tweaks** (archived 2020, no 1.13+ port because "supporting the newest versions of the game would require a major mod rewrite"): sort on R or middle click; three chest sort buttons with modes cycled by middle click; auto-refill of tools/blocks/food; rules file `InvTweaksRules.txt` with `D1 pickaxe` (slot), `D sword` (row), `1 sword` (column), `A5-C9 stuff` (rectangle), `r`/`v` modifiers; `InvTweaksTree.txt` category hierarchy; `InvTweaksCompatibility.xml` for third-party containers. (https://inventory-tweaks.readthedocs.io)
- **Inventory Sorter (Kyrptonaught)**: server-side, works with vanilla clients via middle-click/double-click; **Chest Inv Sort**: "type (block > item) first, then by name". **Quark**: a Sort button on inventory and chests, category-based with per-category rules ("food will get sorted based on which is more filling; tools ... which one is the best, or has more durability; potions ... based on their effects"), plus three chest buttons: pull items that match inventory, deposit all (excluding hotbar/armor/offhand), deposit matching (restock). (https://quarkmod.net/)
- **Mouse Tweaks (YaLTeR)**: RMB tweak (drag-place one per slot repeatedly), LMB tweak with item (drag to pick up all matching; Shift-drag to shift-click all matching), LMB tweak without item, Wheel tweak (scroll down moves items out one at a time, scroll up pulls in). API: implement `IMTModGuiContainer3Ex` (`MT_getSlots`, `MT_getSlotUnderMouse`, `MT_isCraftingOutput`, `MT_isIgnored`, disable flags) or annotate `@MouseTweaksIgnore` / `@MouseTweaksDisableWheelTweak`. Includes autonomous client gametests that "emulate input". (https://github.com/YaLTeR/MouseTweaks)
- **Item Scroller (masa)**: "moving items in inventory GUIs by scrolling the mouse wheel over slots", plus shift+scroll whole stacks, drag-move, mass craft, villager trading helpers. (https://github.com/maruohon/itemscroller)
- **Sophisticated Backpacks**: upgrade slots (pickup, magnet with radius, filters allow/block/match-contents), slot memory ("memorized slots' contents are ignored by sorting"; memory ignores NBT), sort button, tabs for upgrade settings where shift-click prefers the open tab.
- **AE2 terminals**: same prefix grammar as JEI, plus sync-with-JEI/REI search, remember last search, auto-focus.
- **Just Enough Resources (JER)**: JEI addon categories for mob drops, dungeon loot, ore generation graphs by Y level, plant drops, villager trades; `/profile` scans a generated world into `world-gen-scan.json`. Shows the category API is general enough for non-crafting "recipes". (https://www.curseforge.com/minecraft/mc-mods/just-enough-resources-jer)
- **Terraria** as comparison: 10-slot hotbar bound to 0-9, 40 main slots filled "starting from the bottom right", 4 coin and 4 ammo slots (ammo consumed "starting from the top slot"), a trash slot that permanently removes the previous occupant, armor/vanity/accessory slots with right-click auto-equip; chest buttons Loot All, Deposit All, Quick Stack (moves stacks to any chest already containing that item), Sort; Alt+click favorites an item so it is skipped by trash, quick stack and sort; Quick Stack to Nearby Chests from the player inventory. (https://terraria.wiki.gg/wiki/Inventory)

## Key takeaways for a Bevy plugin set

1. Split into two crates/plugins: a generic inventory-UI plugin (slots, containers, drag/carry, shift-click, tooltips, sort/quick-stack) and an optional "item browser overlay" plugin that only depends on the first one's public geometry and slot API, the way JEI depends only on `AbstractContainerScreen`.
2. Model the browser's unit as an `Ingredient` (type id + value + subtype/comparison fn), not an item stack; register ingredient types in a resource-backed registry with renderer, display name, uid, grouping uid, mod/namespace, tags. Items, fluids and "info pages" all become entries.
3. Use explicit registration phases as ordered Bevy schedule sets or a builder that runs on startup: subtypes → ingredient types → categories → recipes → transfer handlers → screen handlers → runtime available. Validate cross-references at the phase boundary.
4. A `RecipeCategory` trait/registry entry provides id, title, icon, size and a `layout(&mut LayoutBuilder, &Recipe)` that emits slots with roles (input/output/catalyst/render-only) and optional custom widgets; the overlay owns focus highlighting, cycling alternatives, bookmarks and hit-testing.
5. Screen integration is a component/registry keyed by screen kind with priority: bounds provider, exclusion rects, clickable areas that open a category, stack-under-cursor provider, ghost-drop acceptor. Re-run layout on screen open, window resize or UI-scale change (JEI's "dirty" gui properties cache).
6. Give the overlay its own z-band: draw its backgrounds beneath container contents, its foreground above them, and route tooltips and the carried item above everything; implement with distinct render layers or `ZIndex` bands and a shared "tooltip queue" so only one tooltip is drawn.
7. Input layering: the overlay claims events inside its rectangles first; a `has_keyboard_focus` flag must gate hotkeys so R/U/A do not fire while any text field is focused, and container text fields must be able to opt out of overlay auto-focus.
8. Search: tokenizer with quoted phrases, `-` negation, `|` OR, `\` escape and single-character prefixes mapped to per-field indexes; each prefix has ENABLED / REQUIRE_PREFIX / DISABLED modes. Index names and tooltips in a suffix automaton or trigram/substring index; put low-cardinality fields (mod, tag, tab) in a string→bitset map; intersect bitsets; cache the last result and invalidate on filter text / hidden set / visibility changes.
9. Build the index off the main thread (async task) with a placeholder "loading" state, and rebuild incrementally when entries are added or hidden rather than from scratch.
10. Render only the visible page of the grid; keep per-entry render data (baked icon handle) in the index element; build tooltips lazily on hover.
11. Transfer handlers take a `dry_run: bool` and return `Result<(), TransferError { missing_slots, message }>` so the `+` button state and red slot highlights come from the same code path; offer a "simple" variant that just takes slot ranges (JEI `IRecipeTransferInfo`, EMI `StandardRecipeHandler`) and a full trait for exotic containers.
12. Keep server authority for anything that mutates the world: cheat-give, recipe fill, delete. Client sends a request; server checks permission (creative/op/game rule) and replies with a permission packet that disables the mode client-side.
13. Make bookmarks/favorites a typed, serializable registry (item, recipe, arbitrary action) as REI does, stored per player profile; allow drag-reordering and "craft from bookmark".
14. Treat hiding/blacklists and "recipe defaults" as data-pack style config (JSON in asset dirs) with an in-game edit mode that exports them, so pack authors can curate without code.
15. Ship dev tooling from day one: highlight exclusion areas, show ids/NBT in tooltips (F3+H analogue), copy recipe id, log untranslated tags, and an event/runtime API (`filter_text`, visible entries, key bindings) so sibling plugins (storage terminals, WAILA-style HUD, sorting) can synchronize with the overlay instead of reimplementing it.
